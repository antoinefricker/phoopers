# Spec 003 — Phase 1c: the editor

**Roadmap phase:** 1 (sub-project 1c of 1a–1d)
**Date:** 10/10/2026
**Depends on:** [spec 001](001-09-10-2026-model-animation-engine.md) — the animation engine, implemented;
[spec 002](002-09-10-2026-2d-view-playback.md) — the 2D view and playback, implemented.

## Overview

An editor that builds a `Play` by hand, so that a play exists because a coach authored it
rather than because someone wrote TypeScript. A coach starts from an empty court, places
players, moves the transport to an instant, drags a token, and a keyframe is written at that
instant. Motion is therefore expressed as positions in time, which is what the model already
stores: the editor's output is the model, with no intermediate representation.

Alongside the court, a timeline shows every entity's keyframes on its own row and lets them be
retimed and removed. The court answers _where_, the timeline answers _when_.

The editor writes `Play` values that the 1a engine resolves and the 1b view renders, both
unchanged. `PlaybackContextProvider` already recomputes its timeline when the `play` it is
given changes identity, so a committed edit propagates through the existing seam.

## Scope

In scope: placing and removing players, a starting formation, moving players and the ball to
write keyframes, a multi-track keyframe timeline with retiming and deletion, creating and
editing named steps, creating screens, forking branches from a step, deleting entities with
confirmation, and surfacing validation issues.

Out of scope: persistence of any kind (1d), curve handles (see [Deferred](#deferred)), undo
and redo, printing and vector export, and the 3D view (Phase 2).

## Modes

One screen with a Play/Edit toggle. In Play mode the 1b view behaves exactly as it does today.
Entering Edit mode pauses playback and makes the court manipulable. There is no separate route:
the application has no router, and two modes do not justify introducing one.

## The editor module

`apps/pwa/src/editor/` is headless and pure, built like the engine: functions of the shape
`(play, args) => Play` that return a new `Play` and never mutate in place. They have no React
dependency and are tested without a DOM.

The module is the only place that knows how to change a play. Components never assemble a
`Play` themselves.

| Function                                                                                         | Effect                                                                                          |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `addPlayer(play, team)`                                                                          | Appends a player with the next free label, and a keyframe at `t=0`                              |
| `removePlayer(play, playerId)`                                                                   | Removes the player and every track, screen and reference to it                                  |
| `applyFormation(play)`                                                                           | Places five offense and five defense in the standard starting formation, with the ball attached |
| `setKeyframe(play, branchId, entityId, t, position)`                                             | Writes a position keyframe, replacing any keyframe already at `t`                               |
| `attachBall(play, branchId, t, playerId)`                                                        | Writes a ball keyframe attached to a player                                                     |
| `releaseBall(play, branchId, t, position)`                                                       | Writes a free-position ball keyframe                                                            |
| `moveKeyframe(play, branchId, entityId, fromT, toT)`                                             | Retimes a keyframe                                                                              |
| `removeKeyframe(play, branchId, entityId, t)`                                                    | Removes a keyframe                                                                              |
| `addStep(play, branchId, t, name)` / `renameStep` / `moveStep` / `removeStep`                    | Step lifecycle                                                                                  |
| `addScreen(play, branchId, t, screenerId, beneficiaryId)` / `setScreenDuration` / `removeScreen` | Screen lifecycle                                                                                |
| `forkBranch(play, parentBranchId, forkStepId, name)`                                             | Creates a branch with empty tracks                                                              |
| `removeBranch(play, branchId)`                                                                   | Removes the branch and its descendants                                                          |

## State ownership

`EditorContextProvider` / `useEditorContext` follows the project's context convention. It owns
the current `Play` and the current selection — the selected entity and the selected keyframe —
and exposes the module's functions already bound to that state. It is the single point through
which every mutation passes.

It wraps `PlaybackContextProvider` and passes it the current `play`. The playback layer's
contract is unchanged.

## Committing an edit

A mutation is committed on pointer release, not during the gesture. While the pointer is down,
a transient preview layer follows it and the affected path redraws translucently; the model is
untouched. This bounds the work to one `resolveBranch` per gesture rather than one per frame,
which matters because resolving rebuilds the arc-length tables for every span.

## Building a play

A new play starts with an empty court and no players. Two ways to populate it:

- **Add a player** places one offense or defense token, labelled with the next free number, at
  the centre of the court, to be dragged into place.
- **Starting formation** places five against five at once in a standard formation, with the
  ball attached to the point guard.

Placing a player writes a keyframe at `t=0` in the root branch. A player is never left without
one, because
[a player with no track vanishes silently](../limitations.md#a-player-with-no-track-vanishes-silently).

An incomplete play is the normal state while building. Nothing blocks on validity.

## Editing motion on the court

With the playhead at an instant, dragging a player token writes a position keyframe for that
player at that instant on the active branch. A keyframe already at that instant is replaced;
otherwise one is created.

The ball uses the same gesture with two outcomes: dropped on a player it becomes an attachment
keyframe, dropped on open court it becomes a free-position keyframe. The model has no separate
notion of a pass, a dribble or a shot — a pass is two consecutive attachments, a dribble is
attachment to a moving player, and a shot is a free position. The editor therefore offers no
pass tool, and a shot authored this way is
[indistinguishable from a pass](../limitations.md#a-shot-is-indistinguishable-from-a-pass) in
the rendering.

Keyframes are written without curve handles, so authored paths are straight between keyframes.

## The timeline

A panel below the court, sharing the transport's time axis so one playhead crosses both. One
row per entity: a row per player plus one for the ball, so eleven rows at five against five.
A left gutter carries each token and its label. The panel scrolls vertically; the time axis always shows the whole duration.

A keyframe is a diamond on its row. The ball's row reads differently from the others: a segment
tinted with the holder's colour while the ball is attached, a hollow diamond where it is free.
Possession is therefore legible across the whole play, not only at the current instant.

Clicking a keyframe selects it and moves the playhead to its time, so the court shows the state
that keyframe describes. Pressing delete removes it, except where it is a player's last
keyframe on the root branch: that one is refused, for the same reason placing a player writes
one. Removing the player is the way to remove their last keyframe.

Dragging a keyframe horizontally retimes it. The gesture is constrained so that an invalid
state cannot be produced rather than being produced and then reported:

- a keyframe cannot cross its neighbours, preserving the model's monotonic ordering;
- a keyframe cannot move before its branch's fork time;
- it snaps to nearby step times, reusing `snapToStep` from the 1b transport.

At each bound the drag stops instead of creating an issue.

Moving the last keyframe of a play changes its duration, because duration is derived from the
model rather than stored. The transport resizes accordingly during the gesture.

## Steps

A dedicated ruler above the entity rows. A step is added at the playhead and named; it can be
renamed, removed, and dragged to retime under the same constraints as a keyframe. The
transport's existing snapping marks follow from the same step data.

## Screens

A screen links a screener to a beneficiary over a duration. It is created by selecting the
screener, choosing to place a screen, then clicking the beneficiary on the court; it is born at
the playhead with a default duration. It renders as a bar on the screener's timeline row, and
its right edge is dragged to set the duration — it is the only object in the model with
temporal extent, so the timeline is where its duration is set.

## Branches

The 1b branch tree gains the ability to fork: from a selected step, a new branch is created
with empty tracks and inherits everything before the fork from its ancestors.

On a non-root branch, nothing before the fork time is editable. The playhead may be moved there
to review inherited motion, but that region of the timeline is dimmed and tokens are not
draggable. This is a rule of the model — a keyframe before the fork is invalid — made visible,
so that an edit a coach believes they are making to a variant cannot silently produce an
invalid play.

## Deletions

Removing a player, a step, a screen or a branch requires an explicit confirmation, since the
editor has no undo. Removing a branch removes its descendants, and the confirmation says so
rather than only doing it.

## Validation

`validatePlay` runs on every committed play. Issues are listed in an unobtrusive panel, each
one clickable to move the playhead and selection to the entity at fault. The panel never
blocks editing: a play under construction is invalid by nature.

## Conventions

- All user-facing strings go through `t()`. Player labels, step names and branch names are
  data and are not translated.
- Reach for Mantine first, composing custom components from its primitives. The court is plain
  SVG by necessity, and the timeline is a drawing surface for the same reason; both stay themed
  through Mantine's CSS variables.
- The context follows the `XxxContextProvider` / `useXxxContext` pattern, with the hook throwing
  outside its provider.

## Testing

- **Pure units** — every editor function, tested headlessly: that each returns a new `Play`,
  leaves the input untouched, and produces a play `validatePlay` accepts where it should. Drag
  constraints (neighbour crossing, fork bound, snapping) are pure functions and are tested as
  such.
- **Components** — Testing Library: adding a player renders a token and writes a `t=0`
  keyframe; dragging commits on release and not before; a keyframe row renders one marker per
  keyframe; deleting a keyframe removes it; a non-root branch refuses edits before its fork;
  deleting a branch asks first.
- **Acceptance** — a play built entirely through the editor's own functions, from an empty
  court to players, motion, a ball, a step, a screen and a fork, and `validatePlay` returns no
  issues.

**Known coverage gap:** pointer-drag gestures over an SVG surface are not meaningfully testable
in jsdom, for the same reason as
[layout is not testable in jsdom](../limitations.md#layout-is-not-testable-in-jsdom). The
constraint arithmetic is therefore separated from the gesture handling so that the part that
can be tested is.

## Acceptance criteria

A coach can, in the browser and without writing code, start from an empty court and produce a
play with players on both teams, motion authored by dragging tokens on a timeline, a ball that
is passed and shot, at least one named step, at least one screen, and at least one alternative
branch forked from a step — then switch to Play mode and watch it back. `validatePlay` reports
no issues on the result.

This is the bar the roadmap sets for the end of phase 1, less persistence, which is 1d.

## Deferred

- **Curve handles.** The model supports `handleIn` / `handleOut` and the sample play uses them,
  but authoring a curve requires a tangent-dragging interaction of its own. Paths authored in
  1c are straight between keyframes. A coach will want to curve a cut around a screen, so this
  is the first candidate for the phase that follows.
- **Undo and redo.** The timeline makes keyframe mistakes visible and directly correctable,
  which covers the common case. It does not recover a position overwritten by a drag.
- **Temporal zoom** on the timeline. A play lasts seconds, so the whole duration fits.
- **Editing `Play.court`**, which switches FIBA and NBA dimensions.
